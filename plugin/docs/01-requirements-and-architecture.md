# 01 · 需求与架构

状态：设计冻结。实现已完成阶段 0–2（宿主 seam 合同 / `domain` 内核 / `adapters/dsh`），阶段 3（性能与真实 wire）未开始。当前 `main` 是**已发布基线**（含恢复与 fork 覆盖增强）。**产品验收仍未通过**，更不代表已安装或已上 npm。逐项已验证 / 未验证 / 不支持见[当前状态](<05-current-status.md>)，覆盖增强见[07](<07-lifecycle-recovery-coverage.md>)。接口依据是本机安装的 Core `0.2.1-alpha.1` 公开接口核验，证据见[运行时证据](<04-runtime-evidence.md>)。

本文只描述**设计与取舍**；实现口径、路径与失败语义以源码为准（[`domain/`](../domain/)、[`adapters/dsh/`](../adapters/dsh/)），与本文的已知差异集中列在 [02 §12](<02-protocol-and-data-model.md>)。

## 1. 真正要解决的问题

### 1.1 成本来自“过早披露”，不只是序列化方式

初始请求携带每个工具的名称、描述与 JSON Schema，用户观测到工具定义占用超过 60K token，而绝大多数任务只用到其中极小一部分。直接后果：

1. **首轮 prefill / TTFT**：在任何任务成果之前，先让模型处理一张巨大的工具表。
2. **持续上下文成本**：后续每一轮都重复携带未使用的工具，挤占代码、材料与推理空间。缓存命中可缓解计算或计费，但**不会让这些数据从上下文中消失**。
3. **选择困难**：大量语义相近的接口、长描述与多家同类适配器争夺注意力。
4. **发现与使用被混为一谈**：模型必须从全部参数细节里推断“我需要什么能力”，而这两个决策本应分开。
5. **安全与维护复杂度**：目录来自动态注册的插件与 MCP；外部描述不应成为系统指令，工具变化也不能被固定静态清单掩盖。

把同一份全量数据改写成 Markdown、压缩 JSON 或技能正文，只要仍然整份注入模型，问题就原样存在。需要改变的是**何时、向谁、披露哪些**。

### 1.2 需求拆成六项产品能力

| 能力 | 用户需要的结果 | 明确不包含 |
|---|---|---|
| 能力导航 | 首轮知道“可以做什么”，但看不到完整清单 | 枚举每个工具及其参数 |
| 名称浏览 | 按类别分页查看可发现工具名 | 返回完整描述/schema，或自动追完所有页 |
| 类别内检索 | 用自然语言在相关类别内找到少量准确候选 | 搜到即全部加载 |
| 显式选定 | 模型选定候选版本，或本次精确名称的当前定义 | 每次都必须询问用户 |
| 工具技能加载 | 获得适用边界与使用指导 | 只返回一段说明文本 |
| 原生执行 | 用原名称、原参数、原执行链调用 | 通用 `execute(name, args)` 转发器 |

### 1.3 “目录 / 数据库入口”的含义

它是模型可查询的**能力目录接口**，不预设首版必须采用关系型数据库。

权威源始终是宿主当前 registry 与 scope 可见性；目录是它投影出的**只读、可检索索引**。否则会出现“目录里有、运行时不存在 / 已撤权 / schema 已过期”的错位。

首版采用：不可变目录快照 + 本地检索索引（token 集合 + 有界线性扫描打分，无倒排结构；数百量级下实测成本可忽略）+ scope 资格视图。数百量级工具不需要引入数据库驱动、embedding 服务或外部网络。规模、冷启动或跨进程共享需求经测量证明必要后再换索引后端；对模型的协议不变。

## 2. 目标、非目标与边界

### 2.1 必须达成

- 默认首轮只出现 `tool_list` / `tool_search` / `tool_load` 三个小入口与有界类别摘要，不预展开普通工具名。
- `list` 按类别分页返回**完整名称**，不带描述/schema，不自动加载。
- `search` 返回少量候选短摘要，不返回参数 schema，不改变激活集合。
- `load` 接受候选引用或精确名称；只激活模型明确选定、当前合格、版本经过核验的工具。
- 下一轮最终出站请求的原生 `tools` 数组包含所选工具的**真实** schema。
- 不绕过宿主的 registry 解析、原输出类型、审批、沙箱、参数校验、超时、取消、调度与 UI 展示。
- 加载状态按逻辑会话隔离；检索缓存按 scope / 资格隔离。
- 支持工具新增、撤除、同名替换、schema 变化，以及会话恢复、压缩、分叉与子代理。
- 输出有界、激活有预算、失败可解释、验收可证伪。

### 2.2 首版明确不做

- 向量数据库、在线 embedding、云端工具市场、自动安装工具。
- 按模型名定制多套发现算法。
- 泛用执行代理或 RPC 转发执行器。
- 默认批量加载整个类别，或默认预载一批“常用工具”。
- 默认用子代理替主模型完成工具搜索（那只是把同样的成本转移给另一个模型）。
- 修改宿主核心，或声称支持未经验证的核心版本。
- 兼容非 native 展示模式：它们可能在 SDK prompt 中另行泄露全量能力，必须另作适配。
- 静默 LRU 卸载：它会让历史调用、模型记忆与实际可用能力三者不一致。

### 2.3 三入口的框架例外

某些 agent 拥有框架强制的结构化输出 / 终止工具，隐藏它会让 agent 无法结束。

普通会话只保留三个控制入口；框架必需工具通过**可信、显式配置**声明保留，并计入初始预算与报告。**不按名称含 `output` / `result` 自动豁免**。无法证明必要性时拒绝该组合，不放宽到全量目录。

## 3. 交互形态

```text
首轮：tool_list / tool_search / tool_load + 有界类别摘要

自然语言需求 → tool_search(category, query) → 少量候选 ref+revision ──┐
                                                                   │
浏览类别     → tool_list(category, cursor) → 只有名称的分页 ────────┤
                                                                   ▼
已知精确名称 ───────────────────────────────→ tool_load
                                               │
                                    资格/版本/预算重新验证
                                               │
                                    技能 + canonical 成功回执
                                               │
                                    下一轮原生 tools 披露 schema
                                               │
                                          调用原工具
```

优化目标是**披露量**，不是把入口数量压到最少；三项小 schema 的成本必须计入首轮实测（目标见[预算表](<02-protocol-and-data-model.md> §9)）。

- `list` 解决“类别里有什么”，也是搜索兜底。
- `search` 解决“哪个能力适合当前任务”，是任务驱动的首选。
- `load` 解决“选定哪些版本”。

不默认走 `list → search → load` 三轮；已知名称不强制先搜一次；不预先展开名称清单。

名称加载是对当前 scope 精确名称的**新**显式选择；候选加载额外约束该 `ref` 绑定的版本（`revision` 可省略，缺省即取该值）。两条路径都不执行目标工具，都必须等下一轮真实 schema 出现后再调用。

`load` 的语义是拉取工具使用技能，不冒用既有文件系统 skill 名称，也不假设通用 skill 能改写 registry。技能载荷只提供规范化使用指导，**禁止复述 schema**（见 `02` §6）。

## 4. 六类数据必须分开

| 数据 | 位置 | 何时进入模型 |
|---|---|---|
| `CategoryCard` | 可信类别配置 + 统计 | 首轮或类别页；有限类别与模糊用途 |
| `NamePage` | 名称投影 | `tool_list` 返回分页名称，不附描述/schema |
| `CandidateCard` | 检索投影 | `tool_search` 返回少量 ID、用途、版本 |
| `ToolSkill` | 按工具版本的技能资源 | 选定后返回可信使用指导 |
| `NativeToolSchema` | 宿主当前 registry | 下一轮原生 `tools` 列表 |
| `ExecutionDefinition` | 宿主 registry 内部 | **永不**作为目录内容返回 |

执行函数、UI callback、服务对象与内部凭据不进入目录协议。schema 原样保留有效字段，**不**以截断参数、删除 `required` 或改写 `enum` 的方式压缩。

## 5. 分层架构

```text
                      模型 / Agent Loop
                       │ list/search/load │
                       ▼                 │
                DiscoveryController      │
                  │        │      │      │
          List/Search    SkillLoader   │
                  │        │      │      │
              CatalogSnapshot     │      │
                  ▲        │      │      │
           RegistryAdapter │      │      │
                  │    SessionStateReducer
             宿主 registry   ▲      │      │
                           │      │      │
                  Canonical result    │
                       journal        │
                                     ▼
                        RequestProjection（system-prompt/assemble）
                                     │
                            原生 tools 子集
                                     │
                        ExecutionDisclosureGuard（tools.guard）
                                     │
                                     ▼
                              宿主原执行链
```

职责边界：

### 5.1 RegistryAdapter — 资格事实的唯一入口

- 读取当前 agent scope 实际可见的工具，而非全局工具全集。
- 判定当前展示模式；非 native 模式在激活期即拒绝。
- 生成不可变 schema 快照与版本摘要。
- 在 `load` 与执行前重新核验工具解析结果。
- 监听工具变化并使相关索引与版本失效。

“可见”不等于“本次执行必定允许”。文件权限、审批与沙箱可能依赖具体参数，只有原执行链能判断；目录**不得**宣称“搜到了就可执行”。

### 5.2 CatalogSnapshot — 共享内容，隔离资格

- 相同 schema 内容的词元、检索文档（token 集合）与技能版本可共享。
- 某会话有权发现的 ID 集合不可全局共享。
- 同名工具被 scope-local 覆盖时，以该 scope 的真实定义为准。
- 公开 API 拿不到稳定 provider 身份时不猜来源，不把名字前缀当授权身份。
- 目录不得扫描其它会话的工具、技能或私有描述。

实现上应把“schema 内容缓存”与“scope 资格缓存”分离，避免每个 agent 为全部工具重复建索引。

### 5.3 List / Search — 发现不产生激活副作用

`List` 从同一 scope 资格视图按稳定顺序分页返回名称；游标绑定会话、view、category、资格代次与有效期。只读浏览，不生成 `ref`、不自动追完全部页、不返回用途或 schema。类别页与状态查询同样挂在 `tool_list`，且仍有界。

`Search` 首次算法：类别过滤 → 精确名称/ID 匹配 → 双语词法检索 → 有界重排 → 候选卡片。

- 中文按 unigram + bigram；英文做小写化、轻量词形归一，并拆分下划线与 namespace。
- 同义词来自**受控词表**（中英双向），不依赖描述恰好包含用户关键词。
- `category` 是查询约束，不是可信授权条件。
- 不相关查询返回零命中，不凑满 K。
- 不依赖 LLM 生成检索结果，避免额外一次模型往返与注入风险。
- 精确名称测试只是协议正确性测试，**不是**自然语言检索质量指标。

### 5.4 SkillLoader — 版本校验与激活事务

`tool_load` 的 load 输入是候选引用 **或** 当前 scope 的精确名称，**两种数组不可混用**。名称不做模糊匹配，不当作文件路径，不绕过权限。

顺序：

1. 验证参数与会话；候选路径核验 `ref` 归属与有效期，名称路径视为一次新的明确选定。
2. 按当前 scope 解析实际绑定，锁定本次定义验证快照。
3. 核验定义 / 技能版本；候选路径要求与 `ref` 绑定的 revision 一致（`revision` 可省略，缺省即取该值），名称路径选择当前版本。`ref` 绑定签发时的版本，工具此后变化仍按陈旧候选拒绝，不会因省略 `revision` 而放行新定义。
4. 估算新增完整 schema 与技能预算；**提交前重核**资格与版本，变化则整批失败。
5. 构造版本化加载回执，记下真实版本与 `selectionSource`，**不执行**目标工具。
6. 回执经宿主原结果链写入 canonical `tool/result`。
7. reducer 核验 call 与回执后才更新 `selected`。
8. 下一轮真实 `request/header` 才建立 `advertised`。

`load` 表示“下一轮生效”，不是执行。取消、后处理失败或 post-policy 失败都不提前激活。

### 5.5 RequestProjection — 真正减少模型输入

形态：`system-prompt/assemble` 投影 + `tools.guard` 单调执行门禁。

- 从已组装、已遵守宿主 scope restriction 的原生 schema 中，选择三个入口、显式框架保留项与本会话有效 `selected` 工具。
- 只减少工具，不复制执行定义、不重注册目标工具、不改变原名称。
- schema 取自本次真实 assembly，不用目录旧缓存替代。
- 与其它 waterfall 组合时，在 `await next()` 之后校验并作最终投影；不能假设自己是最后一层。
- 通过最终 `request/header` 与 provider 请求验证，检查后续 listener 或 adapter 是否重新加回工具。

这一层能覆盖 scope 自身注册的工具，不受 `restrict()` 对自身注册的豁免影响。但**过滤只改变模型输入**，因此必须配合下一层门禁；仅做过滤不构成安全实现。

**重要限制**：宿主 assembly 在 waterfall 之前仍会收集并克隆全量 schema。本方案减少的是**出站模型输入**、prefill 与上下文占用，不自动消除宿主的全量组装 CPU/内存；该成本单独计量，不伪装成已优化。

### 5.6 ExecutionDisclosureGuard — 只增加拒绝，不授予权限

通过披露门禁的条件：

```text
可通过披露门禁
  = 当前会话已完成恢复
  ∧ 调用来自受管理的 agent
  ∧ 工具是入口 / 可信框架保留项，或已成功选定
  ∧ 当前请求确实向该模型展示过此工具及同一 schema 版本
  ∧ 当前 registry 仍解析到匹配定义
```

返回 `undefined` 只表示本插件不拒绝；宿主其它策略仍可拒绝。返回拒绝理由时，目标工具的 body 不应运行。

- 不依据模型自报的 `loaded=true` 或检索结果决定执行。
- 不以全局同名工具兜底；不自动执行 load 请求里的工具。
- 门禁是同步的；恢复与索引构建必须提前完成，未就绪则 fail closed。
- 同一响应中并列 `load` 与一个此前隐藏工具的调用，后者仍应拒绝，即使调度顺序恰好让 `load` 先完成。
- 以 canonical `request/header` 记录 `advertised`；调试或预览态的 assemble 不算真实曝光。
- 首版要求一个活动 agent 独占其会话的模型请求；同一 session 多 agent 同时发请求时，仅凭最近 header 无法无歧义绑定，必须拒绝该组合或实现经验证的 request/call 绑定，**不可声称支持**。

宿主门禁位于 pre-execute / 审批之后，因此隐藏工具的恶意调用可能先触发其它策略询问，但不应进入 body。不能承诺完全消除无效调用的审批 UI。

### 5.7 SessionStateReducer — 日志是真相，内存是缓存

以**本插件成功 `load`/`unload` 的 canonical `tool/call` → `tool/result` 对**作为可恢复 journal：

- 输出 renderer 产出严格版本化 JSON 回执，禁止夹入整套 schema。
- 通过 `sourceEventSeqs`、call ID、工具名、原始 action、协议版本与候选版本核验回执归属。
- 内存 reducer 监听已接受的 session 事件，而不是在 execute body 内提前改最终状态。
- 冷恢复通过公开 session query 读取并验证原始日志，一次折叠后转为增量处理。
- 恢复必须**先订阅并缓存新事件，再读 query 快照**；按 seq 折叠快照、合并缓存并去重，最后切换 ready，避免“读快照与挂监听之间”丢掉 load/unload。恢复失败时注销订阅并保持不可执行。
- 被压缩出当前模型 surface 的结果仍可能存在于原始 durable log；恢复不能只扫描模型当前消息。
- canonical 结果若被其它插件改写为不可验证文本，**不激活**。

## 6. 生命周期与异常场景

### 6.1 会话与子代理

- 普通 spawn：空 `selected`，只有发现入口及其必需框架工具。
- resume：折叠本会话成功 journal，再与当前 registry / 权限取交集；`advertised` 必须由新请求重新建立。
- fork：历史可继承，**能力状态默认不继承**；只折叠 fork 自己拥有的操作，不从继承前缀恢复父 `selected`。
- compaction：不把摘要里写着“工具已加载”当 journal。
- 会话销毁 / HMR：注销 listener、prompt section、门禁与缓存引用；卸载插件本身不是一次用户 `unload` 操作。

### 6.2 定义热变化

- 工具撤除或被限制：立即从下一轮 projection 移除并拒绝执行，状态标 `invalidated`。
- 同名 schema / 描述 / 技能变更：旧引用失效，须重新检索与加载；不静默扩大参数能力。
- 新工具注册：加入目录，不自动激活。
- 权限撤回：`selected` 不产生任何重新授权效果。
- **进行中调用的热替换窗口**：宿主执行链先跑门禁，再经执行 waterfall，然后重新解析实际 body；因此单次门禁中的版本检查**不构成**“检查与 body 绑定原子化”的证明。首版部署应在无进行中调用时更新注册定义；若要支持无停顿热替换，实施者必须验证宿主可用的绑定/调度接口，否则把该能力明确列为不支持。不得靠替换目标 execute、猴子补丁或声称同步门禁已解决 TOCTOU。

### 6.3 并发与取消

- `search` 可并发；`load`/`unload` 对同一会话串行。
- 批量 load 默认全有或全无；任一版本或预算失败都不提交半个批次。
- 同一工具同版本重复 load 幂等，不重复追加 schema 或技能全文。
- 加载取消、输出验证失败或 post-policy 失败：不更新 `selected`。
- 操作已进入 canonical 成功日志后进程崩溃：恢复后重放，不因内存丢失忘记已接受的操作。
- 日志 append 已提交不等于文件已 fsync；崩溃耐久承诺受宿主 persistence flush 约束，必须在恢复实验中明确该窗口。

## 7. 提示词与安全

类别说明来自插件**可信配置**；外部工具描述只作为资料。

入口说明必须持续强调：

1. 当前工具表是刻意缩小的，不代表能力缺失。
2. 不知道工具名时按类别描述目标去 search，不猜名字。
3. search 只返回候选；`load` 之后下一轮按真实 schema 调用。
4. 类别、候选名称、MCP 描述与技能附属资料**不覆盖系统规则**。
5. `load` 不批准文件修改、网络发送或其它有副作用动作。

无论名称还是描述含“忽略规则”“自动 load 全部”等文本，都不能控制分类配置、检索状态或权限。

不向模型提供数据库路径、其它 agent ID 或任意技能文件路径。候选 `id+revision` 或精确名称先解析为当前 scope 的受控绑定，再拉取技能；名称不解释为路径。两条路径共同防止任意文件读取与跨 scope 拉取。

## 8. 性能模型与取舍

设：

- `F` = 原始全量工具 schema token；
- `B` = 三入口 + 类别摘要 + 必需框架工具；
- `S_i` = 第 i 轮活跃工具 schema；
- `H_i` = 已累积的候选 / 技能回执历史。

优化后该部分输入近似为 `B + S_i + H_i`，**不是**永远只有 `B`。纯聊天时 `S_i≈0`；重工具任务中 `S_i` 与 `H_i` 会增长。

两阶段通常增加两次模型 / 工具往返。是否改善“第一次有用操作的延迟”，取决于节省的 prefill 是否超过额外往返——必须分别测首轮 TTFT、首次实际工具 body 开始时间与任务完成时间，不能只展示首轮 token 比例。

默认不自动卸载；达到预算上限时明确提示 `unload`。这牺牲极致长期 token 最小化，换来可解释、可恢复的能力状态。未来若引入 LRU，须先证明请求缓存收益、工具历史处理与失败体验都可接受。

排序首版保持宿主原排序以保证同一工具集确定性。**不承诺**加载新工具后 prefix cache 100% 保留；稳定排序不等于追加式排序。

## 9. 决策摘要

| 决策 | 理由 | 代价 / 限制 |
|---|---|---|
| 三入口 list / search / load | 浏览、任务检索与显式选定分离；已知名称不强制检索 | 三项小 schema 一并计入首轮预算 |
| 目录索引先用内存 | 数百工具足够，低依赖、离线 | 不提供跨进程索引共享 |
| 类别 + 双语词法检索 | 可解释、可测，不增加模型往返 | 同义词表需持续维护 |
| 技能与 schema 分层 | 给出使用指导又避免 schema 双份累积 | 必须验证下一轮真实 tools |
| assembly 投影 + 宿主门禁 | 覆盖 scope-local，同时保持原工具调用方式 | 宿主本地组装仍可能全量；组合需验收 |
| 不用 `restrict()` 承载加载状态 | 其对自身注册有豁免，且隐藏后资格查询困难 | 不宣称与原生 `UNKNOWN_TOOL` 错误一致 |
| 不用 `deferLoading` 作基础 | 本机对应适配器明确拒绝，且它不是完整发现/加载协议 | 放弃 provider 专属优化 |
| 以成功 `tool_load` 的 canonical 结果作 journal | 使用宿主已知事件，不自造持久化格式 | renderer / meta 改写需检测 |
| `native-only` | 非 native 路径可能在 SDK prompt 另行泄露全量工具 | 支持范围较小但诚实 |
| 子代理默认独立发现 | 不把父能力与大 schema 隐式带给子代理 | 子代理多一次发现轮次 |
| 一会话一活动模型 agent | 无法仅凭最近 header 无歧义绑定请求与调用 | 并发共享 session 的组合被拒绝 |
